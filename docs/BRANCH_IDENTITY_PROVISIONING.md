# تأسيس هوية المؤسسة والفرع وتوزيعها

## الهدف والنطاق

هذه الآلية تصدر هوية مؤسسة واحدة وهوية فرع واحدة مرة واحدة، وتتيح تثبيت الهوية نفسها على جميع أجهزة الصيدلية. لا تنشئ UUID عند تشغيل التطبيق، ولا تتصل بخدمات Firebase، ولا تصدر Custom Claims.

## الملفات والحدود الأمنية

- `tools/provisioning/issuer.js`: أداة إصدار محلية باستخدام Node.js المدمج فقط.
- مفتاح Ed25519 الخاص وملف سجل الإصدار يجب أن يبقيا في وسيط/بيئة إدارية آمنة خارج المستودع، ويفضل أن يكون المفتاح غير متصل بالشبكة.
- المفتاح العام فقط هو الذي يوزع داخل التطبيق بعد تثبيته كمرجع موثوق.
- ملف JSON الناتج هو ملف التوزيع المشترك؛ انسخ الملف نفسه دون إعادة توليده إلى كل أجهزة الفرع.
- سجل الإصدار `identity-registry.json` يمنع إصدار هوية ثانية من سجل التأسيس نفسه. احتفظ بنسخة احتياطية آمنة منه مع المفتاح الخاص.
- لا ترفع المفتاح الخاص أو سجل الإصدار أو ملف الهوية التشغيلي إلى GitHub.

## الاستخدام

تهيئة مفتاح التوقيع مرة واحدة:

```sh
node tools/provisioning/issuer.js init-keys --key-dir /secure/offline/pharmacy-issuer
```

إصدار ملف المؤسسة والفرع مرة واحدة:

```sh
node tools/provisioning/issuer.js issue \
  --key-dir /secure/offline/pharmacy-issuer \
  --output /secure/distribution/pharmacy-branch.json \
  --tenant-name-ar "اسم المؤسسة" \
  --branch-name-ar "اسم الصيدلية"
```

التحقق الإداري من سلامة الملف:

```sh
node tools/provisioning/issuer.js verify \
  --manifest /secure/distribution/pharmacy-branch.json \
  --public-key /secure/offline/pharmacy-issuer/provisioning-ed25519-public.pem
```

## قواعد التشغيل

1. يصدر المسؤول الملف مرة واحدة ويحفظ نسخة احتياطية من سجل الإصدار والمفتاح الخاص.
2. يوزع الملف الموقع نفسه عبر قناة موثوقة إلى كل جهاز تابع للفرع.
3. يجب أن يتحقق العميل من توقيع Ed25519 باستخدام المفتاح العام الموثوق المضمن في إصدار التطبيق قبل أي كتابة.
4. بعد التحقق، يستبدل العميل المعرفين المؤقتين `tenant-main` و`branch-main` داخل معاملة SQLite واحدة، ويتحقق من عدم وجود بيانات سحابية أو هوية تأسيس مختلفة قبل التغيير.
5. يسجل العميل `issuance_id` لمنع إعادة تطبيق الملف، ويقفل هوية التأسيس بعد اعتمادها. لا يسمح باستيراد ملف مختلف إلا بإجراء إعادة تأسيس إداري موثق.
6. لا يُصدر `branch_id` في Firebase Claims إلا بعد اعتماد UUID الفرع ومراجعة ربط UID بالفرع.

## حالة التنفيذ والقيود

- **منفذ في هذه المرحلة:** مولد هوية Tenant/Branch، توقيع Ed25519، تحقق CLI، سجل يمنع الإصدار المتكرر، واختبار Node.js يغطي التوقيع والتلاعب وإعادة الإصدار.
- **منفذ برمجياً:** مستورد Flutter يتحقق من التوقيع ويطبق الهوية داخل SQLite، وشاشة استيراد تتطلب رمز المالك، واختبارات على قاعدتي SQLite مستقلتين. المفتاح العام لا يزال يحتاج إلى تضمينه في إصدار التطبيق المخصص للتأسيس، ولم يصدر manifest إنتاجي بعد.
- **متبقي:** توزيع ملف التأسيس نفسه على الجهازين، مقارنة UUID المؤسسة والفرع ومعرّفي الجهاز، وإكمال تسجيل الجهاز لدى جهة موثوقة وربط tenant_id بقواعد Firebase قبل الإنتاج.
- لذلك لا تستخدم الملف لتفعيل المزامنة أو إصدار Claims الآن. تبقى الهوية المؤقتة الحالية كما هي حتى يكتمل مستورد Flutter واختباره.
- في نموذج المؤسسة متعددة الصيدليات مستقبلاً: يبقى `tenant_uuid` للمؤسسة ثابتاً، ويصدر لكل فرع `branch_uuid` مستقل بعملية إدارية معتمدة؛ لا يمنح `tenant_uuid` وحده وصولاً تلقائياً إلى كل الفروع.

## مستورد Flutter — تثبيت الهوية على الأجهزة

- شاشة إعدادات النظام ← السحابة ← «تأسيس هوية المؤسسة والفرع» تسمح للمسؤول باختيار ملف JSON.
- المستورد يتحقق من بنية الملف وحقوله وإصدار المخطط وUUIDs، ثم يتحقق من توقيع Ed25519 مقابل مفتاح عام موثوق يمرر عند بناء التطبيق عبر `PROVISIONING_ED25519_PUBLIC_KEY_PEM`.
- لا يقبل التطبيق أي ملف إذا كان المفتاح العام غير مضبوط، أو إذا تغير أي حقل موقع، أو استُخدم مفتاح مختلف.
- بعد التحقق، يحدّث سجل المؤسسة والفرع ويسجل `issuance_id` في معاملة SQLite واحدة. يتم تأجيل فحص المفاتيح الخارجية إلى نهاية المعاملة لتحديث UUID المؤسسة والمرجع التابع بأمان.
- تُنشأ قيود SQLite تمنع تعديل/حذف UUID المؤسسة والفرع أو حذف سجل التأسيس بعد نجاح العملية. كما يمنع المستورد إعادة التطبيق، حتى لو كان الملف نفسه.
- اختبار `test/branch_identity_provisioning_test.dart` يغطي تثبيت الملف نفسه على قاعدتين مستقلتين، ورفض التلاعب، ورفض المفتاح غير الموثوق، ورفض إعادة التثبيت، وحماية الهوية على مستوى SQLite.

### تهيئة المفتاح العام للتطبيق

بعد إنشاء المفتاح خارج المستودع، حوّل المفتاح العام فقط إلى Base64:

```sh
base64 -w0 /secure/offline/pharmacy-issuer/provisioning-ed25519-public.pem
```

ضع الناتج في GitHub Repository Variables بالاسم:
PROVISIONING_ED25519_PUBLIC_KEY_PEM_BASE64

المتغير عام وليس سراً. يمرره Workflow إلى Android Release وWindows Release ويحوّله التطبيق إلى PEM عند تشغيل مستورد الهوية. إذا لم تضبط المتغير أو كانت قيمته غير صالحة، يبقى زر الاستيراد معطلاً ويرفض التطبيق أي ملف.

لا ترفع المفتاح الخاص أو سجل الإصدار إلى GitHub، ولا تمرر المفتاح الخاص إلى Flutter أو إلى أجهزة الصيدلية. المفتاح الخاص يبقى في بيئة الإصدار الإدارية الآمنة.

**تنبيه تشغيلي:** لم يصدر manifest إنتاجي ولم يتم اعتماد UUID فعلي حتى الآن. لا تجرِ التأسيس على أجهزة التشغيل قبل نجاح CI، وتحديد أسماء المؤسسة والفرع النهائية، وإعداد المفتاح العام الصحيح في Repository Variables.
 
## ضوابط إضافية لمستورد التطبيق

- يتطلب الاستيراد تحقق رمز المالك فعلياً عبر `verifyOwnerPin`؛ إدخال أي نص في نافذة التأكيد لا يكفي.
- الإصدار الحالي مخصص لقاعدة بيانات مؤسسة ذات فرع واحد فقط. إذا اكتشف المستورد أكثر من سجل فرع (حتى لو كان بعضه محذوفاً منطقياً) يرفض العملية كاملة دون تعديل.
- يتم تثبيت المفتاح العام عبر build-time define. لا تضع المفتاح الخاص في `--dart-define` أو أي ملف تطبيق.
- حالة التأسيس وسجلها والقيود الواقية تنشأ ضمن معاملة التثبيت نفسها؛ فشل أي خطوة يعيد المعاملة إلى الحالة السابقة.


## معرّف كل جهاز على حدة

- يحتفظ التطبيق بمعرّف UUID v4 عشوائي لكل تثبيت في flutter_secure_storage عبر DeviceIdentityService، ولا يخزنه داخل SQLite أو النسخة الاحتياطية.
- لذلك عند تثبيت التطبيق على جهازين واستيراد ملف التأسيس نفسه، يشترك الجهازان في tenant_uuid وbranch_uuid، بينما يكون لكل منهما device_id مختلف.
- يرفض المستورد الآن إعادة التأسيس إذا كان إعداد المزامنة رقم 35 مفعلاً، أو وجدت دفعات Outbox مكتملة أو سجلات Inbox موجودة؛ الهدف منع تغيير namespace بعد بدء المزامنة.
- يضيف FirestoreSyncWorker الحقل source_device_id إلى مستند دفعة المزامنة. الغرض منه تتبع مصدر الدفعة والتشخيص فقط؛ لا يمنح الجهاز صلاحية دخول ولا يحل محل Firebase ID token أو Custom Claims.
- إعادة تثبيت التطبيق قد تنشئ device_id جديداً؛ هذا معرف تثبيت وليس بصمة عتاد دائمة.
- لا تنسخ قاعدة SQLite من الجهاز الأول إلى الثاني بغرض تأسيس الهوية. استورد ملف JSON الموقع نفسه على الجهازين، ثم قارن شاشة إعدادات النظام ← السحابة: يجب أن يتطابق UUID المؤسسة والفرع ويختلف معرّف الجهاز.
- لم يتم تسجيل الأجهزة لدى خادم موثوق أو إصدار مفاتيح/Claims حية في هذه المرحلة. اعتماد الجهاز أمنياً يحتاج خطوة تسجيل خادمية لاحقة؛ لا تثق بـsource_device_id وحده.

## التحقق من أمان أداة الإصدار

يرفض الأمر issue الآن كلاً من مجلد المفاتيح ووجهة ملف manifest إذا كان أي منهما داخل جذر مستودع Git، حتى لو كانت ملفات المفتاح موجودة مسبقاً. يغطي tools/provisioning/issuer.test.js هذه الحالة لمنع تسرب المفتاح الخاص أو سجل الإصدار إلى Git بالخطأ.
