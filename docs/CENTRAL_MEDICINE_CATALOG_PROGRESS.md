## ما اكتمل

- تأكدنا أن `drugs` الحالي سجل تشغيلي مرتبط بالمبيعات والمشتريات والمخزون والوصفات والتقارير؛ لذلك لا نستبدله.

- لا يوجد خادم مركزي أو API production في المستودع؛ لا عنوان وهمي ولا مفاتيح افتراضية.

### المرحلة 2 — البحث والذاكرة المحلية

الملفات المضافة:
- `lib/data/models/catalog_drug_model.dart`
- `lib/data/services/central_catalog_api.dart`
- `lib/data/repositories/catalog_search_repository.dart`
- `test/catalog_search_repository_test.dart`

السلوك المنفذ:
- البحث النصي لا يبدأ قبل حرفين.
- حد الصفحة 30 نتيجة حتى لو طلب المستدعي رقماً أكبر.
- البحث الرقمي من 8 إلى 14 خانة يرسل كـ exact barcode.
- نتائج API تُخزن داخل `catalog_cache` في معاملة واحدة.
- عند انقطاع الاتصال يعاد البحث من الذاكرة المحلية، مع `offlineFallback` ورسالة الخطأ.
- FTS5 يُختبر وقت التشغيل؛ إذا فشل الإنشاء أو البحث يستخدم LIKE كبديل.
- cache الافتراضي 10,000 نتيجة غير مرتبطة بأدوية مختارة؛ لا يحذف العناصر التي يشير إليها `drugs.catalog_uuid`.
- يمنع تخزين إصدار أقدم فوق إصدار أحدث.
- لا ينشئ هذا الجزء سجلات في `drugs` أو مخزوناً أو دفعات.

الاختبارات المضافة تغطي:
1. صفحة بعيدة محدودة وتخزين النتائج والـ cursor.
2. exact barcode والعودة للذاكرة عند offline.
3. البحث المحلي وتجاهل المدخل القصير.
4. الاحتفاظ بمرجع الدواء المختار عند تنظيف cache.

6. منع تراجع نسخة الدواء عند وصول إصدار أقدم متأخر.

## المرحلة 3 — شاشة اختيار الأدوية من الموسوعة

- أضيفت `lib/screens/drugs/central_medicine_picker_screen.dart` وربطت من شاشة الموسوعة الحالية بزر «اختيار من الموسوعة» مع إبقاء الإضافة اليدوية منفصلة.
- البحث التدريجي يستخدم تأخير 300ms. عند تغير الاستعلام يُلغى مؤقت البحث السابق ويُرفع رقم جيل الطلب؛ أي استجابة قديمة تصل لاحقاً يتم تجاهلها ولا تستطيع استبدال نتائج البحث الأحدث.
- لا يجري تحميل أكثر من 30 نتيجة في الصفحة، والصفحة التالية تستخدم `next_cursor` من API عبر زر «تحميل 30 نتيجة أخرى».
- تفاصيل النتيجة تُعرض عند فتحها، ثم يمكن الإضافة بزر صريح «إضافة إلى صيدليتي».
- الإضافة تنشئ سجل `drugs` محلياً مع `catalog_uuid` و`catalog_version`، وبسعر وتكلفة ومخزون صفري؛ لا تنشئ دفعة أو حركة مخزون.
- عنوان API يُمرر وقت البناء عبر `--dart-define=CATALOG_API_BASE_URL=...`. لا يوجد عنوان إنتاجي مضبوط في المستودع حالياً؛ لذلك تعمل الشاشة على الذاكرة المحلية وتوضح أن الاتصال المركزي غير مضبوط حتى توفير عنوان صالح.
- **قيد الإلغاء:** طلب HTTP الجاري لا يُجهض على مستوى socket باستخدام عقد HTTP الحالي؛ لكنه يُبطل منطقياً فور كتابة استعلام أحدث، وتُهمل استجابته القديمة. يمكن إضافة إلغاء نقل فعلي عند اعتماد عميل HTTP يدعم abort/cancellation.

**شرط الإطلاق:** قبل تمكين المزامنة، يجب إعداد Authentication وcustom claims من جهة موثوقة، وتنفيذ idempotent batch processor، واختبار قواعد Firestore عبر Emulator، والتحقق من أن التطبيق لا يضع بيانات مرضى أو سجلات حساسة في حزم غير محمية.



## المرحلة 6 — Firestore outbound worker وInbox idempotent (2026-11-08)

**الحالة: أضيف التنفيذ البرمجي والاختبارات؛ يلزم CI ثم ربط موفر هوية Firebase والتحقق باستخدام Emulator قبل تفعيل التشغيل الفعلي.**

### عامل الرفع إلى Firestore
- إضافة `FirestoreSyncWorker` باستخدام Firestore REST API حتى لا نفرض إضافة FlutterFire plugins غير المدعومة بالتساوي على Android وWindows.
- يقرأ `sync.cloud` (الإعداد 35): `enabled`, `provider=firestore`, `project_id`, `database_id`، و`batch_size` (1–100). رُبط الآن `SettingsAndSystemProvider.syncNow()` مباشرة بـ`FirestoreSyncWorker.syncConfigured()`، ويستخدم رقم الفرع الفعّال من جلسة التطبيق بدلاً من القيمة الافتراضية الثابتة.
- يلتقط عناصر `sync_queue` للفرع الحالي فقط، ويحوّل العلاقات المحلية ذات المفاتيح الرقمية إلى مراجع UUID عامة في `relations`.
- يستخرج UUID الفرع من سجل `branches` المحلي ويستخدمه في مسار Firestore والـcustom claim؛ لا يستخدم رقم SQLite المحلي كهوية سحابية. يكتب دفعة واحدة كوثيقة append-only في `pharmacy_sync_batches/{branchUuid}/batches/{batchUuid}`، مع بصمة SHA-256 وهوية batch ثابتة مشتقة من محتوى الأحداث. عند إعادة الإرسال بعد timeout، يتحقق من وجود الوثيقة وبصمتها قبل اعتبار العملية ناجحة.
- لا يعلّم صفوف المصدر `SYNCED` ولا عناصر queue `DONE` إلا بعد تأكيد كتابة Firestore؛ فشل النقل يعيد الصفوف إلى `FAILED` لإعادة المحاولة.
- يلتزم بحد 100 حدث وبحد حجم محافظ للوثيقة. يسحب الوارد باستعلام Firestore مرتباً زمنياً مع cursor محلي حتى لا يعيد قراءة كامل سجل الدفعات في كل دورة، ثم يعيد محاولة الأحداث المؤجلة التي تنتظر سجلات أب.

### Inbox ومعالجة التغييرات الواردة
- ترقية SQLite إلى schema v14 وإضافة `sync_inbox`, `sync_inbox_batches`, `sync_inbox_cursors`.
- يسجل كل حدث بمفتاح فريد `(branch_id,event_uuid)` وبصمة محتوى؛ إعادة الحدث نفسه لا تعيد تطبيقه، وإعادة استخدام الهوية بمحتوى مختلف ترفض.
- يطبّق كل حدث وتسجيل حالة Inbox ضمن معاملة SQLite واحدة.
- يرفض الجداول الحساسة/المحلية مثل users وsystem_settings وaudit_logs وsync_queue، ولا يقبل إلا جداول تملك uuid وbranch_id وsync_version وsync_status.
- يعيد ربط المفاتيح الأجنبية عبر UUID الأب بدلاً من افتراض تطابق أرقام SQLite بين الأجهزة، مع استثناء `branch_id` الذي يظل محلياً؛ ويؤجل الحدث بحالة `NEEDS_DEPENDENCY` إذا لم يصل الأب بعد، ثم يعيد محاولة المؤجل بعد كل سحب.
- يمنع تحديث سجل محلي أحدث أو غير متزامن حتى لا يطمس تعديلاً محلياً؛ ويعيّن السجلات الواردة `SYNCED` لمنع إعادة إرسالها كأحداث محلية. تُرفض إعادة استخدام event UUID أو batch UUID ببصمة مختلفة.
- يمنع العامل رفع جداول الأطراف والمرضى والوصفات والبيانات السريرية والموظفين الحساسة، ويضع عناصرها في `CONFLICT` حتى تتوفر طبقة تشفير وإدارة مفاتيح معتمدة؛ كما يرفضها Inbox الوارد.

### الحدود المتبقية قبل التشغيل الحي
