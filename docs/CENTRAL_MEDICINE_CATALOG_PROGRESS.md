**المرحلة 2: تنفيذ الكود والاختبارات أضيف إلى الفرع؛ ينتظر CI للتحقق.** Repository للبحث المحلي/البعيد، exact barcode، تخزين النتائج، offline fallback، وإدارة حجم الذاكرة.

## ما اكتمل

### المرحلة 0 — المعمارية والتدقيق

- تأكدنا أن `drugs` الحالي سجل تشغيلي مرتبط بالمبيعات والمشتريات والمخزون والوصفات والتقارير؛ لذلك لا نستبدله.
- قررنا أن الخادم المركزي سيكون مصدر البيانات المرجعية، وأن SQLite في الفرع تحفظ نتائج البحث المختارة فقط.
- لا يوجد خادم مركزي أو API production في المستودع؛ لا عنوان وهمي ولا مفاتيح افتراضية.

### المرحلة 1 — SQLite v13

- `schema_iteration10.dart`: إضافة `catalog_uuid` و`catalog_version`، وإنشاء `catalog_cache` و`catalog_sync_state`.
- `database_helper.dart`: رفع إصدار قاعدة البيانات إلى 13.
- `test/database/catalog_migration_test.dart`: ترحيل قاعدة v12 فيها دواء تشغيلي، وإعادة تنفيذ الترحيل، والتحقق من بقاء الاسم والكود والأسعار والرصيد وسلامة المفاتيح الخارجية.
- CI: Run 42419098865 — Android وWindows ناجحان، Analyze وTests وAPK وWindows Release ناجحة.

### المرحلة 2 — البحث والذاكرة المحلية

الملفات المضافة:
- `lib/data/models/catalog_drug_model.dart`
- `lib/data/services/central_catalog_api.dart`
- `lib/data/repositories/catalog_search_repository.dart`
- `test/catalog_search_repository_test.dart`

السلوك المنفذ:
- البحث النصي لا يبدأ قبل حرفين.
- حد الصفحة 30 نتيجة حتى لو طلب المستدعي رقماً أكبر.
- البحث الرقمي من 8 إلى 14 خانة يرسل كـ exact barcode.
- نتائج API تُخزن داخل `catalog_cache` في معاملة واحدة.
- عند انقطاع الاتصال يعاد البحث من الذاكرة المحلية، مع `offlineFallback` ورسالة الخطأ.
- FTS5 يُختبر وقت التشغيل؛ إذا فشل الإنشاء أو البحث يستخدم LIKE كبديل.
- cache الافتراضي 10,000 نتيجة غير مرتبطة بأدوية مختارة؛ لا يحذف العناصر التي يشير إليها `drugs.catalog_uuid`.
- يمنع تخزين إصدار أقدم فوق إصدار أحدث.
- لا ينشئ هذا الجزء سجلات في `drugs` أو مخزوناً أو دفعات.

الاختبارات المضافة تغطي:
1. صفحة بعيدة محدودة وتخزين النتائج والـ cursor.
2. exact barcode والعودة للذاكرة عند offline.
3. البحث المحلي وتجاهل المدخل القصير.
4. الاحتفاظ بمرجع الدواء المختار عند تنظيف cache.
5. FTS5 أو fallback.
6. منع تراجع نسخة الدواء عند وصول إصدار أقدم متأخر.

**مهم:** لم يتم تشغيل CI للمرحلة 2 بعد. لا تعلن نجاح Analyze أو الاختبارات أو البناء قبل ظهور Run مكتمل ونتيجته success.

## نقطة التوقف الدقيقة

- المرحلة الحالية: 2 — Repository والبحث المحلي/البعيد.
- الخطوة المباشرة: انتظار CI للـ commit الذي يحتوي الملفات أعلاه؛ إذا فشل، اقرأ سجل الخطأ وأصلح السبب ثم أعد CI.
- بعد نجاح CI: المرحلة 3 — بناء شاشة «اختيار الأدوية من الموسوعة» وربطها بالـ Repository.
- لا تنشئ API أو تنشر PostgreSQL قبل تحديد بيئة الاستضافة والمصادقة ومصادر البيانات الطبية.

## قائمة الاستئناف

1. تحقق من رأس `feature/central-medicine-catalog` ولا تفترض SHA ثابتاً.
2. اقرأ هذا الملف و`CENTRAL_MEDICINE_CATALOG_ARCHITECTURE.md`.
3. راجع أحدث CI وسجلات Android/Windows.
4. أصلح كل فشل قبل الانتقال للواجهة.
5. عند إنشاء شاشة الاختيار، أضف debounce في الواجهة (نحو 300ms) وإلغاء الطلب السابق/تجاهل النتائج القديمة.
6. اجعل تحميل التفاصيل السريرية منفصلاً عن نتائج البحث.
7. لا تنشئ الصنف التشغيلي حتى يضغط المستخدم «إضافة إلى صيدليتي».
8. عند الإضافة، حافظ على السعر/المخزون المحلي ولا تنشئ دفعة أو حركة مخزون.
9. حدّث سجل التقدم وCHANGELOG ثم شغّل CI كاملاً.
