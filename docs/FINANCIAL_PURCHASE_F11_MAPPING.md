# F11 — خريطة الآثار الفعلية لفاتورة الشراء قبل عقد النقل

**الحالة:** SOURCE MAPPED / TRANSPORT BLOCKED. هذا جرد مستند إلى `PurchaseAndBonusService.postInvoice` على الفرع `feature/central-medicine-catalog`. لا يغير الترحيل المحلي ولا يفعّل نقل المشتريات.

## حدود معاملة المصدر

`postInvoice` ينفذ داخل `Database.transaction` واحدة. الإدخالات والتعديلات التالية تشترك في نجاح المعاملة أو تراجعها:

| الجدول | الأثر | شرط الربط على الوجهة |
|---|---|---|
| `purchase_invoices` | إدخال رأس الفاتورة، ثم تحديث `journal_entry_id` | UUID جديد موثوق للفاتورة؛ المورد والمستودع والفرع بمراجع UUID |
| `purchase_invoice_items` | إدخال بند لكل عنصر | UUID للبند والصنف؛ عدم نقل `invoice_id` الرقمي |
| `batches_fefo` | إنشاء دفعة جديدة أو تعديل دفعة موجودة؛ كمية وتكلفة وموقع | UUID ثابت للدفعة والمخزن، وحسم تطابق الدفعة التاريخية قبل النقل؛ لا last-write-wins للكمية |
| `stock_movements` | `PURCHASE_IN` و`BONUS_IN` بحسب الكميات | إنشاء الحركة مرة واحدة وربطها بالدفعة والفاتورة |
| `drugs` | تحديث المخزون ومتوسط التكلفة وآخر تكلفة شراء، وقد يتغير سعر البيع | الأرصدة مشتقة من الحركة؛ لا تُنسخ `stock_total_units` كحقيقة مستقلة |
| `price_history` | سجل `COST_AVG` لكل بند، و`SELL_PRICE` اختيارياً | `source_doc_id` محلي؛ يحتاج UUID للفاتورة |
| `lah_alayh_ledger` | استحقاق المورد، ودفعة سداد إذا كان `paidTotal>0` | هوية القيد لا تُشتق من `invoiceId` المحلي |
| `cash_accounts` | تخفيض `current_balance` عند السداد | إعادة حساب الرصيد من الحركة المعتمدة، لا استبدال قيمة مرسلة |
| `cash_transactions` | حركة `PURCHASE_PAYMENT` عند السداد | هوية حركة مستقلة ومرجع الصندوق والوردية |
| `journal_entries` / `journal_lines` | `postBalancedEntry` ثم ربط القيد بالفاتورة | تطبيق مباشر مع تحقق التوازن والعملة، دون إعادة استدعاء `postInvoice` |
| `purchase_order_items` / `purchase_orders` | تحديث المستلم وحالة الطلب عند وجود `purchaseOrderId` | أثر شرطي يجب تضمينه أو رفض نقل العملية حتى حسمه |

## فجوات محددة في المصدر

1. `purchase_invoices` و`purchase_invoice_items` لا يُمرر لهما UUID عند الإدخال في المسار المفحوص؛ لا يمكن افتراض وجود هوية عامة مستقرة دون مراجعة المخطط أو triggers.
2. `batches_fefo` الجديدة لا يُمرر لها UUID؛ التاريخية قد تفتقر لهوية مشتركة بين الجهازين.
3. `lah_alayh_ledger.uuid` يُبنى حالياً من `purchase-ledger-` أو `purchase-payment-` مع `invoiceId` المحلي؛ هذه **ليست UUID عالمية** وقد تتصادم بين جهازين.
4. `cash_transactions` وحركات المخزون ومراجع `source_doc_id` تستخدم أرقاماً محلية؛ يلزم عقد تحويل UUID قبل أي إرسال.
5. يتعامل المسار مع `CASH` و`CREDIT` و`PARTIAL`، ومع بونص وتكاليف وخصومات وضرائب؛ لا يجوز إسقاط حالة من العقد دون رفض صريح.
6. لا يوجد استدعاء لالتقاط `financial_operation_outbox` داخل هذه المعاملة في المصدر المفحوص.

## شروط التنفيذ دون تكرار

- إبقاء معادلات التكلفة والبونص وترحيل المحاسبة المحلية الحالية؛ لا إعادة كتابة `postInvoice`.
- تثبيت مخطط UUID لكل عضو ومراجع المورد والصنف والمخزن والدفعة والصندوق، وترحيل تاريخي موثوق فقط.
- بناء snapshot غير قابل للتغيير داخل معاملة المصدر بعد اكتمال كل الأعضاء، ثم تحويله إلى wire UUID-only بعد تحقق صارم.
- إضافة تحقق خادم مستقل لـ `PURCHASE`، وتطبيق ذري A→B، ومؤشر مستقل إن لزم؛ منع إعادة الترحيل المحلي على B.
- اختبارات قاعدتين مع IDs مختلفة، وتكرار العملية وتعارض hash وفقد ACK واعتماد مفقود، وتوازن القيد والكمية والبونص.
- يبقى `FinancialDomainGate` رافضاً لنقل `PURCHASE`، ولا تُفتح بوابات الإنتاج قبل CI ناجح وتجربة جهازين وصلاحيات Firebase.
