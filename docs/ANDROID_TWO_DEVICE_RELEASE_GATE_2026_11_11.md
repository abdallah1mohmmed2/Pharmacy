# Android two-device release gate — 2026-11-11

## Verified repository facts
- Firebase project chosen by operator: `pharmacy-dafb6`. Do not commit API keys, refresh tokens, service-account JSON, or private signing keys.
- Target branch: `feature/central-medicine-catalog`; do not modify `main`.
- Flutter Android platform is generated by CI using `flutter create --platforms=android,windows --org com.globalpharmacy .`. Do not assume an `android/` directory exists in source.
- The application uses Firebase Auth and Firestore REST clients, with runtime cloud-sync setting 35 (`project_id`, `api_key`, `database_id`, `enabled`).
- `firebase/firestore.rules` requires a verified Firebase Auth claim `branch_id` equal to the *issued branch UUID*, not `PH1`, and a suitable `branch_role` for privileged reads.
- The existing provisioning issuer and importer must be used; do not regenerate identity for each device.
- Android CI passes, but this does **not** prove production Firestore authorization or two-device synchronization.

## Required one-time, security-sensitive setup
1. On a trusted administrative machine, generate the Ed25519 issuer keypair **outside Git**, back up the private key and issuance registry securely, and issue **one** signed manifest for organization `PHARMACY`, branch `PH1` with `tools/provisioning/issuer.js` as described in `docs/BRANCH_IDENTITY_PROVISIONING.md`.
2. Configure repository Actions variable `PROVISIONING_ED25519_PUBLIC_KEY_PEM_BASE64` with the **public PEM only**, Base64 encoded. Never store the private key or the manifest issuance registry in Actions, Git, or Firestore.
3. Build a fresh Android release on the feature branch and distribute the **same signed manifest** to both Android devices. Back up existing SQLite data before any identity provisioning; never copy device A's SQLite database to device B.
4. From a trusted Firebase Admin environment, grant only the approved user UID access to the **exact issued branch UUID** via verified Custom Claims. Do not use `PH1`, `branch-main`, or any guessed UUID as the claim. Never put Admin credentials on an Android device or in the repository.
5. Configure runtime setting 35 on both devices for `pharmacy-dafb6`, the correct Web API key and `(default)` database, and authenticate with authorized Firebase accounts. Keep sync disabled until branch identity and authorization have been verified.

## Acceptance gate — two independent Android devices
- Both devices show identical issued tenant and branch UUIDs and different device IDs.
- Firestore connection test succeeds on both with the approved claim; an unauthorized user is denied.
- Create a non-sensitive test record on device A, sync, and verify exactly one corresponding record on device B. Repeat B → A.
- Repeat sync without changes; verify no duplicate records, financial entries, or batches. Exercise reconnect after temporary network loss.
- Validate supported transaction categories and server-side event validation separately. Keep financial sync and production rollout disabled until these tests and a trusted financial relay are accepted.
- Record test date, application commit/build artifact, two device identifiers (non-secret), test results, and any failures.

## Stop conditions
- No trusted issuer private key / no single signed manifest.
- No approved Admin Custom Claims for the actual branch UUID.
- Firestore authorization denied or untested.
- No independent two-device end-to-end result.
- Financial relay HTTPS endpoint not deployed and validated.

A green CI build and a successful local login are not sufficient evidence to claim first-day cross-device synchronization.
